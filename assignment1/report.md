## 摘要

本项目实现了可配置 N×N 棋盘、K 子及以上连珠获胜的广义五子棋，提供人人、人与 AI、AI 与 AI 三种对战模式，以及图形界面和命令行入口。AI 遵循 Gomoku AI Protocol v1，采用迭代加深 Negamax、Alpha-Beta 剪枝和主变搜索，以动态生成的 K 格窗口构造评估函数，并结合增量威胁索引、着法排序、置换表、静态搜索和有限连续威胁证明搜索。

本报告对应已经冻结的 Aegis 3，所有数值来自实际运行。2026-10-10 的短时实验中，默认搜索设置在 9×9 四连和 15×15 五连下分别对随机 AI 进行 40 局，均为 40 胜、0 平、0 负；另完成自我对战和深度上限对比。此前同一版本在每步 5 秒的条件下，对 Gemini v5 的两局结果为 2:0，对 Gemini v6 的两局结果为 1:1。实验显示程序能够稳定处理这些配置，但随机对手胜率和少量强对手比赛不足以说明普遍棋力。

## 1. 总体设计

### 1.1 游戏规则和模块划分

棋盘采用二维列表，0、1、2 分别表示空位、黑棋和白棋。坐标为从 0 开始的 (row, col)。黑棋先行，每次只能在空位落子；横、竖和两条斜线任一方向连续达到 K 子即获胜，长连同样判胜，没有禁手。棋盘下满且没有连珠时判和。

程序按职责划分如下：

| 文件 | 主要职责 |
| --- | --- |
| main.py | 统一入口，默认启动 GUI，--cli 切换命令行 |
| main_cli.py | 参数解析、三种命令行模式、悔棋和重新开始 |
| gomoku_game.py | 棋盘状态、落子校验、连珠和和棋判定、历史与悔棋 |
| gui.py | Tkinter 棋盘、配置项、状态和历史展示、AI 调度 |
| gomoku_ai.py | 独立的协议 AI，不依赖项目内其他模块 |
| arena.py | 按协议加载 AI、子进程计时、合法性检查和棋谱记录 |
| random_ai.py | 随机合法落子基线 |
| experiments.py | 多配置、交换棋色、自我对战及消融实验 |
| test_gomoku.py | 规则、协议、战术和搜索状态回滚测试 |

游戏引擎是棋局的唯一状态来源。胜负判定从最新落子向四个方向的正反两侧扫描，计算完整连续棋子数量，不把非连续棋子错误地计为连珠。AI 搜索使用独立内部状态，搜索中的模拟落子不会写入真实棋盘。

### 1.2 三种模式

人人对战由两名玩家轮流点击棋盘，或在 CLI 输入行列坐标。人机对战允许选择玩家棋色，轮到 AI 时通过统一接口请求落子。机机对战可以加载两个独立 AI 文件，自动完成对局并记录结果；批量比赛交替先后手。

GUI 使用子进程运行 AI，通过事件循环轮询结果，避免把长时间搜索放在界面线程中。悔棋、重新开始和关闭窗口时会处理对应 AI 进程，防止旧棋局的搜索结果落到新棋盘上。CLI 提供 undo、restart、quit 等命令。

### 1.3 配置与协议

N、K 来自 --board、--win 或 GUI 设置项，统一传给游戏引擎和 GomokuAI。默认 N=15、K=5；实现接受 N>=3、3<=K<=N，覆盖作业规定的 5<=N<=15 范围。棋盘尺寸、获胜长度、候选位置和窗口都由参数计算，不以固定 15×15 或固定五连作为搜索前提。

AI 保持以下接口不变：

```python
GomokuAI(player_id, board_size, win_length)
get_move(board, last_opponent_move, time_limit) -> (row, col)
```

返回值是含两个原生 Python int 的元组。每局重新创建实例；局内可保留搜索缓存，每步以传入棋盘重新构造内部局面，因此不依赖修改 board 或跨局记忆。last_opponent_move 接口保留，当前实现主要从完整棋盘恢复局面。合法但搜索时间极短的输入也会先准备一个合法备用着法；满盘不应再由裁判请求落子。

## 2. AI 算法

### 2.1 Minimax、Negamax 与迭代加深

广义五子棋属于双人、轮流行动、零和的完全信息博弈。本实现用 Negamax 表达 Minimax：当前玩家选择使己方价值最大的落子，而下一层的对手价值取负。

```text
V(position, side, depth)
    = max over legal candidate moves m:
        -V(position after m, 3-side, depth-1)
```

终局使用远大于普通位置分数的胜负值，并结合距根节点的步数，偏好更快获胜。达到深度边界时进行有限战术静态搜索，随后使用评估函数。

迭代加深从深度 1 开始，逐层完成搜索，默认最大深度上限为 64，同时受剩余空位数和时限约束。只有一层搜索完整结束，才更新最终候选。若更深一层超时，返回上一完整层的结果或此前已准备的合法着法。

主要流程的简化伪代码如下。PVS、缓存和静态搜索的细节另见后文。

```text
GET_MOVE(board, side, time_limit):
    校验输入，复制棋盘，准备合法 fallback
    若空棋盘、仅一个空位或预算极短：返回相应合法着法
    按 N、K 建立内部局面与安全截止时间
    若己方可一步连成 K 子：直接获胜
    若对手可一步连成 K 子：优先封堵
    生成并排序候选；识别可立即制造两个获胜点的落子
    在局部预算内搜索己方连续威胁，成功则返回证明着法
    在局部预算内筛查落子后对手的连续威胁
    best = 当前合法候选
    for depth = 1, 2, ...:
        try:
            value, move = NEGAMAX(position, depth, -INF, INF, side)
            best = move           # 本层完整完成后才保存
        except SearchTimeout:
            break
        若搜索给出正向必胜估计：停止继续加深
    return best

NEGAMAX(position, depth, alpha, beta, side):
    检查截止时间及终局、直接获胜点
    若 depth <= 0：返回有限战术静态搜索结果
    在内部节点尝试使用合适的置换表边界
    按强制防守、威胁和位置价值生成候选
    best = -INF
    for move in candidates:
        make(move)
        try:
            score = -NEGAMAX(child, depth-1, -beta, -alpha, 3-side)
        finally:
            unmake(move)
        best = max(best, score)
        alpha = max(alpha, score)
        若 alpha >= beta：停止搜索其他候选
    保存本节点的深度、分数、边界类型和最佳着法
    return best
```

Alpha-Beta 在某分支已不可能改善当前选择时剪枝。PVS 对排序靠前的第一着进行完整窗口搜索，对后续着法先进行零窗口探测，可能改善结果时再扩大窗口重搜。较深迭代使用窄窗口估计，越过窗口边界时重新完整搜索。

由于存在候选截断与有限战术扩展，一般位置的搜索分数仍是选择性搜索估计，不能等同于穷尽全棋盘的博弈论证明。连续威胁搜索与直接双威胁识别的肯定结果有明确战术依据，但也只覆盖所搜索的威胁类型。

### 2.2 随 K 自适应的评估函数

程序枚举横、竖和两条斜线中所有长度恰为 K 的连续窗口。窗口总数为：

```text
W(N,K) = 2*N*(N-K+1) + 2*(N-K+1)^2
```

9×9 四连有 180 个窗口，15×15 五连有 572 个窗口。K 子以上的长连必然包含至少一个长度 K 的窗口，因此这一表示也支持长连获胜。

设窗口 w 中黑、白棋数量分别为 b(w)、c(w)，权重为 weight(0)=0，weight(i)=7^i（1<=i<=K）。基础位置分数从黑棋视角计算：

```text
E_black = sum_w [
    (c(w)==0 ? weight(b(w)) : 0)
    - (b(w)==0 ? weight(c(w)) : 0)
]
E_white = -E_black
```

含双方棋子的窗口已无法在该窗口内连成同色 K 子，因此不计潜力分。未被阻挡的窗口按棋子数量指数增加分数，体现接近连珠时的威胁增长。搜索叶节点按当前行棋方调整符号，并限制普通估值范围，确保它不会压过终局胜负值。

该函数能够处理窗口内部带空位的棋形，不仅计算连续长度。与此同时，它会重复计算重叠窗口的潜力，并且对开放空间、布局协同和长期主动权的描述有限，因此必须与精确威胁识别及搜索配合。

着法排序还有独立的进攻、防守增量项，其中进攻增量乘 10、防守增量乘 11；这个轻微防守倾向属于排序规则，不是上述基础评估函数的额外乘数。

### 2.3 位棋盘、增量更新和威胁索引

内部使用 Python 整数位棋盘，以 row*N+col 映射每个格子。每个窗口保存双方棋子计数，每个格子保存经过它的窗口编号。一次 make/unmake 主要更新经过该格的窗口，最多涉及 4K 个窗口，避免每个搜索节点都重新评估整盘。

对于含 K-1 枚己方棋子、没有对手棋子的窗口，唯一空位是下一步获胜点。程序按空位去重并维护引用计数：多个窗口共用同一获胜点，不会被误计为两个独立威胁。

对于含 K-2 枚己方棋子且剩余两个空位的窗口，维护两个空位之间的联系。若落在某一空位后留下至少两个不同的下一步获胜点，就形成双威胁，对手只能落一子，无法同时封堵。

另外，K-3 窗口用于寻找能够在下一步构建双威胁的准备手，提升这类交点的排序优先级。这部分仅是启发式排序，不把准备手直接声明为已证明获胜；K<4 时不使用这项构建规则。

所有模拟落子均通过 try/finally 回滚，截止时间中断也不会遗留棋子、窗口分数、威胁索引或哈希状态。

### 2.4 候选生成与其他优化

普通候选首先来自已有棋子周围行、列距离不超过 2 的空位；若该集合为空，退回全部空位。另补入双方战术联系索引中的位置，防止关键威胁位置被普通邻域限制遗漏。空棋盘优先中央位置是通用启发式，不是固定应答表。

根节点默认保留排序前 32 个候选；内部节点按剩余深度使用 14 或 12 的基础宽度，同时补入具有直接战术联系的着法。立即获胜和必须封堵的情况绕过普通候选截断。

其他优化包括：

1. Zobrist 哈希和置换表：缓存局面的搜索深度、分数、边界类型与优选着法；键中包含行棋方。
2. 杀手着法和历史启发：优先尝试此前产生剪枝的着法。
3. 晚着法缩减：对排序较后、非强制的安静着法先缩减深度；若结果可能改善 alpha，则恢复深度重搜。
4. 战术静态搜索：深度边界处延伸强制封堵和进攻，减轻在冲四或双威胁途中截断造成的误评。
5. 静态搜索缓存：仅复用剩余战术深度相符的已完成搜索边界，并处理必胜分数的距离编码。

开发中发现过内部节点与根节点候选宽度不一致的问题。如果根节点直接接受较窄内部搜索缓存的负向必胜估计，可能漏掉安静防守。Aegis 3 取消根节点的置换表分数直接截断，仍保留缓存着法用于排序；也不因负向必胜估计提前停止迭代加深。相关行为已有专门回归测试。

### 2.5 连续威胁证明搜索与根节点筛查

标准五连下，VCF 搜索寻找连续冲四：每个进攻着法产生下一步成五威胁，迫使对手封堵，继续搜索后续强制链。这里的判断以 K 为参数，对其他连珠长度寻找对应的强制成连威胁。

进攻阶段依次尝试 4、8、12、18、24 的证明深度上限，使用独立且有限的时间预算。根节点还会尝试模拟候选落子，检查对手是否能发动深度上限为 18 的已证明连续威胁；只有得到肯定证明的着法才加入排除集合。证明失败或超时只代表未证实，不代表该着法安全。若筛查把所有候选排除，仍保留合法落子退路。

这不是完整的威胁空间求解器。它不穷尽所有带安静准备手的进攻，也不能保证发现每个多路布局威胁。

### 2.6 时间与协议安全

搜索使用 time.perf_counter() 管理墙钟时间。内部预算为：

```text
T_internal = max(0, 0.88*time_limit - min(0.012, 0.08*time_limit))
```

每步时限 5 秒时，内部搜索预算约 4.388 秒；0.05 秒时约 0.040 秒。保留时间用于返回、进程通信和调度，搜索及排序过程会检查截止时间。

己方 VCF 阶段最多使用 min(0.65, 0.16*T) 秒，根节点筛查阶段最多使用 min(0.45, 0.10*T) 秒，且均受总截止时间约束。time_limit<0.08 秒时不启动这些 VCF 阶段。不能把很短预算下的实验当作全部证明搜索功能的测试。

裁判使用独立子进程，记录从请求开始到 AI 完成回复的实际时间，并检查返回类型、边界与占用情况。超时进程可以终止；初始化失败、未捕获异常和非法落子均有对应判负路径。保守预算降低超时风险，不能构成任何硬件负载下绝不超时的数学保证。

A、B 使用相同 AI 文件，以下按真实棋色统计获胜数，避免把身份交换后的比分误解为和棋。

| 配置 | 局数 | 黑胜/白胜/和棋 | 各局长度/手 | 平均长度/手 | 双方平均每步/秒 |
| --- | --- | --- | --- | --- | --- |
| 9×9，K=4 | 4 | 4/0/0 | 11、11、11、11 | 11.000 | 0.014427 |
| 15×15，K=5 | 4 | 3/1/0 | 59、56、59、59 | 58.250 | 0.029684 |

自我对战均为正常连珠结束。9×9 四连的四局长度相同，反映确定性中央开局和相同算法容易重复路径；不能把重复开局当作四种独立布局证据。15×15 五连的自我对战明显长于随机对手对局，说明双方能持续封堵和反击。

每种配置只有 4 局，空棋盘开局也缺少多样性。黑棋获胜较多只能描述本次样本，不能据此声称证明先手必胜。

### 3.5 不同搜索深度上限的对比

保持评估函数、种子、棋色数量和每步 0.05 秒预算一致，分别设置 max_depth=2、max_depth=4，以及默认上限 64 的迭代加深。每个设置、每个配置均为 40 局，对手仍为随机 AI。

| 配置 | 搜索上限 | 局数 | 胜/平/负 | 平均每步/秒 | 平均完成深度 | 平均对局/手 |
| --- | --- | --- | --- | --- | --- | --- |
| 9×9，K=4 | 默认 64（迭代加深） | 40 | 40/0/0 | 0.014073 | 0.812 | 7.750 |
| 9×9，K=4 | 2 | 40 | 40/0/0 | 0.006901 | 0.671 | 7.700 |
| 9×9，K=4 | 4 | 40 | 40/0/0 | 0.014041 | 0.732 | 7.700 |
| 15×15，K=5 | 默认 64（迭代加深） | 40 | 40/0/0 | 0.020715 | 1.529 | 9.700 |
| 15×15，K=5 | 2 | 40 | 40/0/0 | 0.004954 | 1.010 | 9.600 |
| 15×15，K=5 | 4 | 40 | 40/0/0 | 0.020704 | 1.529 | 9.700 |

“平均完成深度”来自每步 last_stats.depth，包含首手、直接获胜或强制封堵等不进行常规迭代搜索的 0 层记录；它不是所有搜索分支的实际长度，静态搜索扩展也不计入该层数。深度 4 是上限而非保证每步完成 4 层，默认 64 同理。

三种设置胜率均为 100%，说明该随机基线已经出现胜率饱和。限制为 2 层能减少平均用时，但本实验没有显示更深搜索能提高胜率，不能将这一结果推广为“浅层足够对抗强 AI”。最大深度 4 与默认搜索在 15×15 下的数据非常接近，也反映短预算限制了进一步加深。

实验器还运行了关闭 VCF 的控制组，但 0.05 秒本就低于 VCF 启动阈值 0.08 秒，因此这一控制组不构成有效的 VCF 消融。本报告不利用它推断 VCF 是否有效；评估其贡献需要在更充足且相同的预算下另做对照。

## 4. 讨论与反思

### 4.1 实现中的主要困难

第一，增量状态的正确性比增加搜索深度更基础。窗口重叠、同一空位参与多个威胁、重复联系和中断回滚都可能造成伪威胁。实现采用引用计数，并用重新构建局面和独立规则判定作对照。

第二，缓存必须匹配搜索语义。不同深度、行棋方、战术延伸长度以及候选宽度不能无条件混用。根节点放弃直接采用较窄内部搜索边界，是针对这一问题的修正。

第三，算法需要同时处理棋力和返回时限。增加候选数、证明深度或静态搜索都可能挤占主搜索时间。实现为不同阶段设置小预算，并保留完整迭代层的结果，减少中断导致无有效选择的风险。

### 4.2 当前不足

评估函数主要描述未被阻挡的 K 格窗口，不能充分区分相同棋子数量下的开放性、协同进攻和长远控制。邻域候选、宽度截断和晚着法缩减可以节省资源，也会增加漏掉安静防守或远处准备手的风险。有限 VCF 不覆盖完整威胁空间。

实验方面，随机对手太弱，深度对比的胜率饱和；0.05 秒预算也使 VCF 未参与。自我对战样本小且开局相似，5 秒强对手对局仅四局。因此结论应限定在已测试的配置、版本、对手与预算。

### 4.3 后续改进

后续可以加入受时间约束的安静准备手威胁搜索，并对已找到的威胁链系统检查防守，重点改善多路进攻的早期识别。候选宽度也可以按局面紧迫程度动态调整：战术风险大时优先保证防守覆盖，平静局面再加强位置搜索。

评估函数可以补充可解释的开放端、威胁交点和空间特征，但应通过消融验证是否真正改善决策，而不是只增加权重。验证上应增加成对交换棋色的不同开局、战术局面集、多名搜索对手，以及至少 0.1、1、5 秒的同条件预算对照，再比较胜率、失败类型和计算开销。

## 5. 运行与复现

进入包含上述 Python 文件的 assignment1 目录后，可使用以下命令。AI 核心和 CLI 只依赖 Python 标准库；GUI 额外需要 Python 环境具有可用的 Tkinter/Tcl/Tk，无需额外五子棋引擎或在线服务。本文测试环境为 Python 3.12.14。

```bash
# 默认 GUI；也可在界面中修改模式、N、K 和时限
python main.py --board 15 --win 5

# 人人对战
python main.py --cli --mode human-human --board 9 --win 4

# 人机对战，玩家执白
python main.py --cli --mode human-ai --human-color white --board 15 --win 5

# 机机对战，交换棋色，对随机 AI
python main.py --cli --mode ai-ai --ai-white random_ai.py --games 2 --time 5

# 规则、协议和战术回归
python -m unittest -v test_gomoku

# 本报告的短时随机、自我对战和深度对比实验
python experiments.py --configs 9:4 15:5 --games 40 --self-games 4 --time 0.05 --seed 20261010 --ablation --json report-experiments-aegis3.json

# 正式 5 秒预算的对随机 AI 检查；该命令不属于上文 0.05 秒统计
python arena.py gomoku_ai.py random_ai.py --board 15 --win 5 --time 5 --games 2 --quiet
```

由于截止时间会影响完成深度，重新运行时实际用时和部分棋谱可能随系统调度变化。复现重点是保留源码版本、参数、种子、对手和完整记录，而不是要求每个墙钟时间逐位相同。
